Chrome Performance Tab 学習サンプル

各ボタンをクリックして、DevTools の Performance タブで問題を確認しましょう

JavaScript パフォーマンス問題

1. 長いタスク (Long Task)

メインスレッドをブロックする重い計算処理。Performance タブで赤い三角マークと "Long Task" として表示されます。

原因と対策を見る

原因

  • 同期的なループ処理がメインスレッドを占有
  • 50ms以上かかる処理は「Long Task」としてマークされる
  • Long Task中はユーザー入力やアニメーションが停止
  • ブラウザのレンダリングがブロックされUIがフリーズ

対策

  • Web Worker: 重い計算を別スレッドで実行
  • タスク分割: setTimeout や requestIdleCallback で処理を分割
  • 仮想化: 大量データは仮想スクロールで表示
  • 遅延読み込み: 必要になるまで処理を延期
改善例: 
// 悪い例: 同期処理
for (let i = 0; i < 1000000; i++) { /* 重い処理 */ }

// 良い例: Web Worker
const worker = new Worker('heavy-task.js');
worker.postMessage(data);
worker.onmessage = (e) => console.log(e.data);

2. Layout Thrashing (強制同期レイアウト)

DOM の読み取りと書き込みを交互に行い、強制的なレイアウト再計算を発生させます。紫色の "Layout" が大量に表示されます。

原因と対策を見る

原因

  • DOM の書き込み後に読み取りを行うと、ブラウザは最新のレイアウトを計算する必要がある
  • ループ内で読み書きを交互に行うと、毎回レイアウトが強制的に再計算される
  • レイアウトを強制するプロパティ: offsetHeight, offsetWidth, clientHeight, scrollTop など

対策

  • 読み書き分離: まず全ての読み取りを行い、その後全ての書き込みを行う
  • FastDOM: 読み書きをバッチ処理するライブラリを使用
  • CSS変数: JavaScript の代わりに CSS カスタムプロパティを使用
  • requestAnimationFrame: 書き込みを次フレームに延期
改善例: 
// 悪い例: 読み書きが交互
elements.forEach(el => {
  const width = el.offsetWidth;  // 読み取り
  el.style.width = width + 10 + 'px';  // 書き込み
});

// 良い例: 読み書き分離
const widths = elements.map(el => el.offsetWidth);  // 全て読み取り
elements.forEach((el, i) => {
  el.style.width = widths[i] + 10 + 'px';  // 全て書き込み
});

3. 大量の DOM 操作

1000個の要素を個別に追加。"Recalculate Style" と "Layout" が頻発します。

原因と対策を見る

原因

  • DOM への追加ごとにスタイル再計算とレイアウトが発生
  • 1000回の追加 = 1000回のリフロー（最悪ケース）
  • DOM ツリーの変更はコストが高い操作

対策

  • DocumentFragment: メモリ上で構築してから一度に追加
  • innerHTML: 文字列として構築して一括挿入
  • display: none: 非表示状態で変更し、完了後に表示
  • cloneNode: 切り離したノードで変更後に再追加
改善例: 
// 悪い例: 1つずつ追加
for (let i = 0; i < 1000; i++) {
  container.appendChild(createItem());
}

// 良い例: DocumentFragment
const fragment = document.createDocumentFragment();
for (let i = 0; i < 1000; i++) {
  fragment.appendChild(createItem());
}
container.appendChild(fragment);  // 1回の追加

4. メモリリーク

クリアされない参照を蓄積。Memory タブと併用して確認できます。

蓄積オブジェクト: 0
原因と対策を見る

原因

  • グローバル変数: グローバルスコープに保持された参照
  • イベントリスナー: 削除されない要素に紐づいたリスナー
  • クロージャ: 外部スコープの変数への参照を保持
  • タイマー: clearInterval/clearTimeout されないタイマー
  • DOM参照: 削除済みDOM要素への参照を保持

対策

  • WeakMap/WeakSet: 弱参照を使用してGCを許可
  • 明示的なクリーンアップ: コンポーネント破棄時にリスナーを削除
  • スコープ管理: 必要な範囲でのみ変数を保持
  • Memory タブ: ヒープスナップショットで漏れを特定
改善例: 
// 悪い例: グローバル配列に蓄積
const cache = [];
function addData(data) {
  cache.push(data);  // 永遠に増加
}

// 良い例: WeakMap + 明示的クリーンアップ
const cache = new WeakMap();
function cleanup() {
  // WeakMap は参照がなくなると自動でGCされる
}

5. 頻繁なタイマー

setInterval で高頻度の更新を実行。"Timer Fired" イベントが大量に発生します。

タイマー: 停止中
原因と対策を見る

原因

  • 1ms間隔のタイマーは現実的には約4ms間隔で実行される（ブラウザ制限）
  • 毎回のコールバックでメインスレッドが占有される
  • タイマー内での重い処理は問題を悪化させる
  • バックグラウンドタブでも実行され続ける場合がある

対策

  • requestAnimationFrame: アニメーションには60fpsで最適化されたrAFを使用
  • 適切な間隔: 必要最小限の頻度に設定（例: 100ms, 1000ms）
  • Visibility API: バックグラウンドタブではタイマーを停止
  • スロットリング: 実行頻度を制限
改善例: 
// 悪い例: 高頻度タイマー
setInterval(() => updateUI(), 1);

// 良い例: requestAnimationFrame
function animate() {
  updateUI();
  requestAnimationFrame(animate);
}
requestAnimationFrame(animate);

// 良い例: Visibility APIで制御
document.addEventListener('visibilitychange', () => {
  if (document.hidden) stopTimer();
  else startTimer();
});

CSS パフォーマンス問題

6. 重い CSS アニメーション (非推奨プロパティ)

width/height/top/left のアニメーションは Layout を引き起こします。緑色の "Paint" と紫色の "Layout" が頻発します。

Layout
発生
原因と対策を見る

原因

  • レイアウトプロパティ: width, height, top, left, margin, padding などの変更はレイアウト再計算を引き起こす
  • レンダリングパイプライン: Layout → Paint → Composite の全工程が毎フレーム実行
  • メインスレッドで処理されるため、他の処理をブロック
JavaScript → Style → Layout → Paint → Composite

対策

  • transform を使用: translateX/Y で移動、scale でサイズ変更
  • opacity を使用: 透明度変更は Composite のみ
  • will-change: 変更予定のプロパティを事前に宣言
  • GPUアクセラレーション: transform は GPU で処理される
改善例: 
/* 悪い例: レイアウトを引き起こす */
@keyframes bad {
  from { left: 0; width: 100px; }
  to { left: 200px; width: 150px; }
}

/* 良い例: Compositeのみ */
@keyframes good {
  from { transform: translateX(0) scale(1); }
  to { transform: translateX(200px) scale(1.5); }
}

8. 複雑な CSS セレクタ

深いネストや複雑なセレクタはスタイル計算を遅くします。

原因と対策を見る

原因

  • セレクタの評価順序: ブラウザはセレクタを右から左に評価する
  • 深いネスト: 各レベルで親要素をチェックする必要がある
  • 複雑な疑似クラス: :nth-child, :not などは計算コストが高い
  • 要素数: セレクタは全ての要素に対してマッチングを試みる
遅いセレクタの例: 
.container div.item ul li a.link span { }
div[data-id="1"]:nth-child(odd):not(.excluded):hover { }

対策

  • BEM 命名規則: フラットなクラス名で高速マッチング
  • ID セレクタ: 最速だが、再利用性とのトレードオフ
  • クラスセレクタ: 要素セレクタより高速
  • ネストを浅く: 2-3レベル以内に抑える
改善例: 
/* 悪い例 */
.nav .menu .item .link .icon { }

/* 良い例: BEM */
.nav__icon { }

10. 強制リフロー

offsetHeight などを読み取ると強制的にレイアウトが発生します。

リフロー対象
原因と対策を見る

原因

以下のプロパティを読み取ると、ブラウザは最新のレイアウト情報を返すために強制的にレイアウトを計算します:

  • offsetTop, offsetLeft, offsetWidth, offsetHeight
  • scrollTop, scrollLeft, scrollWidth, scrollHeight
  • clientTop, clientLeft, clientWidth, clientHeight
  • getComputedStyle()
  • getBoundingClientRect()

対策

  • キャッシュ: 値を変数に保存して再利用
  • バッチ処理: 読み取りと書き込みを分離
  • ResizeObserver: サイズ変更の監視に使用
  • IntersectionObserver: 可視性の判定に使用
改善例: 
// 悪い例: ループ内で読み取り
for (let i = 0; i < 100; i++) {
  el.style.width = el.offsetWidth + 1 + 'px';
}

// 良い例: キャッシュして使用
const width = el.offsetWidth;
for (let i = 0; i < 100; i++) {
  el.style.width = width + i + 'px';
}
// 最後に一度だけ読み取り

原因

  • 高頻度発火: スクロールイベントは1秒に何十回も発火

  • 重い処理: DOM操作やレイアウト読み取りが毎回実行される

  • requestAnimationFrame: フレームごとに1回だけ処理

// 悪い例
el.addEventListener('scroll', heavyHandler);

// 良い例: passive + rAF
let ticking = false;
el.addEventListener('scroll', () => {
  if (!ticking) {
    requestAnimationFrame(() => {
      handleScroll();
      ticking = false;
    });
    ticking = true;
  }
}, { passive: true });

JavaScript 追加問題

13. 大量イベントリスナー

1000個の要素に個別にイベントリスナーを追加。メモリ消費とイベント処理時間が増加します。

原因と対策を見る

原因

  • 各リスナーがメモリを消費（関数オブジェクト + クロージャ）
  • イベント発火時、全リスナーをチェック
  • 動的に追加された要素には個別対応が必要
  • リスナーの削除忘れでメモリリーク発生
メモリ使用量の比較: 
1000個の個別リスナー: ~1000個の関数オブジェクト
イベントデリゲーション: 1個の関数オブジェクト

対策: イベントデリゲーション

  • 親要素に1つのリスナーを設定
  • event.target で発生元を判定
  • 動的要素も自動的にカバー
  • メモリ使用量を大幅削減
改善例: 
// 悪い例: 個別リスナー
items.forEach(item => {
  item.addEventListener('click', handleClick);
});

// 良い例: イベントデリゲーション
container.addEventListener('click', (e) => {
  if (e.target.matches('.item')) {
    handleClick(e);
  }
});

14. Debounce / Throttle 比較

入力イベントの最適化効果を比較。下のテキストボックスに連続入力してください。

0回
0回
0回
原因と対策を見る

Debounce と Throttle の違い

手法 動作 用途
Debounce 最後のイベントから一定時間後に1回実行 検索入力、ウィンドウリサイズ
Throttle 一定間隔で最大1回実行 スクロール、マウス移動
タイムライン比較: 
イベント:  |-|-|-|-|-|-----------|
通常:      |x|x|x|x|x|           | (5回実行)
Debounce:  |         |-------|x| | (1回実行、遅延後)
Throttle:  |x|   |x|   |x|       | (3回実行、間隔制限)

実装例

// Debounce
function debounce(fn, delay) {
  let timeoutId;
  return (...args) => {
    clearTimeout(timeoutId);
    timeoutId = setTimeout(() => fn(...args), delay);
  };
}

// Throttle
function throttle(fn, limit) {
  let inThrottle;
  return (...args) => {
    if (!inThrottle) {
      fn(...args);
      inThrottle = true;
      setTimeout(() => inThrottle = false, limit);
    }
  };
}

15. JSON.parse 大量データ

巨大なJSONデータのパース処理。メインスレッドをブロックします。

原因と対策を見る

原因

  • JSON.parse() は同期処理でメインスレッドをブロック
  • 大きなデータほど処理時間が長くなる
  • パース中はUIが完全にフリーズ
  • メモリを一度に確保するためGCも発生しやすい

対策

  • Web Worker: 別スレッドでパース
  • ストリーミング: データを分割して処理
  • サーバー側で分割: ページネーションでデータを小分けに
  • 必要なデータのみ: GraphQL等で必要なフィールドのみ取得
改善例: 
// 悪い例: 同期パース
const data = JSON.parse(hugeJsonString);

// 良い例: Web Worker
const worker = new Worker('json-worker.js');
worker.postMessage(jsonString);
worker.onmessage = (e) => {
  const data = e.data;
  updateUI(data);
};

16. 正規表現の暴走 (ReDoS)

悪意のある入力で正規表現が指数的に遅くなる問題。

原因と対策を見る

原因: バックトラッキング

  • 正規表現エンジンはマッチしない場合、別のパターンを試す（バックトラック）
  • ネストした量指定子 (a+)+ は指数的な組み合わせを生む
  • 悪意のある入力で意図的に遅延させることが可能（ReDoS攻撃）
危険なパターン例: 
/(a+)+$/       // ネストした量指定子
/(a|a)+$/      // 重複する選択肢
/(.*a){10}/    // 繰り返しの中の .*

対策

  • アトミックグループ: バックトラックを防止
  • 所有量指定子: ++, *+ を使用
  • 入力の長さ制限: 処理前にバリデーション
  • タイムアウト: 処理時間に上限を設定
  • safe-regex ライブラリ: 危険なパターンを検出
改善例: 
// 悪い例
/(a+)+$/.test(input)

// 良い例: 具体的なパターン
/a+$/.test(input)

// 良い例: 入力長制限
if (input.length > 1000) return false;
/pattern/.test(input);

レイヤーとレンダリング

17. will-change の乱用

過剰なレイヤー生成によるメモリ消費。Layers タブで確認できます。

原因と対策を見る

原因

  • will-change は要素を独立したコンポジットレイヤーに昇格
  • 各レイヤーはGPUメモリを消費（ビットマップとして保持）
  • 過剰なレイヤーはメモリ不足やクラッシュの原因に
  • レイヤー間の合成処理も増加
メモリ消費の目安: 
1レイヤー (100x100px) ≈ 40KB (RGBA)
500レイヤー = 約 20MB の GPUメモリ消費

対策

  • 必要な時だけ: アニメーション開始時に追加、終了時に削除
  • 最小限の要素: 本当に必要な要素にのみ適用
  • Layers タブで確認: 生成されているレイヤー数をチェック
  • contain: strict: 代替として検討
改善例: 
/* 悪い例: 常に適用 */
.card { will-change: transform; }

/* 良い例: 必要な時だけ */
.card:hover { will-change: transform; }
.card.animating { will-change: transform; }

/* JS で動的に制御 */
el.style.willChange = 'transform';
el.addEventListener('transitionend', () => {
  el.style.willChange = 'auto';
});

18. CLS（レイアウトシフト）

コンテンツ読み込み後にレイアウトがずれる問題。Core Web Vitals の重要指標です。

このテキストの下に画像が読み込まれます。読み込み後にテキストがずれるか確認してください。
このテキストは画像の下にあります。画像読み込みでずれる可能性があります。
原因と対策を見る

原因

  • サイズ未指定の画像や広告が読み込み後にスペースを確保
  • 動的に挿入されるコンテンツ（バナー、通知）
  • Webフォントの読み込みによるテキストサイズ変更
  • 非同期で読み込まれる埋め込みコンテンツ
CLS スコアの計算: 
CLS = Σ (影響割合 × 距離割合)

影響割合: ずれた要素が占める画面の割合
距離割合: ずれた距離の画面に対する割合

良好: < 0.1 | 改善が必要: 0.1-0.25 | 不良: > 0.25

対策

  • 画像にサイズ指定: width/height 属性を必ず設定
  • aspect-ratio: CSSでアスペクト比を維持
  • プレースホルダー: コンテンツ読み込み前にスペースを確保
  • font-display: optional: フォント読み込み遅延時の影響を軽減
改善例: 
<!-- 悪い例: サイズ未指定 -->
<img src="image.jpg">

<!-- 良い例: サイズ指定 -->
<img src="image.jpg" width="800" height="600">

/* CSS でアスペクト比を維持 */
.image-container {
  aspect-ratio: 16 / 9;
  background: #eee;
}

リソース読み込み

20. レンダーブロッキング

同期的なCSS/JSの読み込みによるレンダリング遅延。

ブロッキング:
HTML CSS (待機) JS (待機) Render
非ブロッキング:
HTML Render CSS JS
原因と対策を見る

原因

  • <link rel="stylesheet"> はデフォルトでレンダーブロッキング
  • <script> はHTMLパースを停止して実行
  • 外部リソースの読み込み完了まで描画が遅延
  • CSSOM構築完了までJSも待機する場合がある

対策

<!-- CSS: クリティカルCSSをインライン化 -->
<style>/* 初期表示に必要な最小限のCSS */</style>
<link rel="preload" href="full.css" as="style"
      onload="this.rel='stylesheet'">

<!-- JS: async または defer -->
<script src="app.js" defer></script>
<script src="analytics.js" async></script>

<!-- リソースのプリロード -->
<link rel="preload" href="font.woff2" as="font"
      crossorigin>
<link rel="preconnect" href="https://api.example.com">
属性 動作
async 並列ダウンロード、即座に実行（順序不定）
defer 並列ダウンロード、DOMContentLoaded前に順序通り実行

21. 画像の遅延読み込み

Lazy Loading による初期読み込みの最適化。Network タブで確認できます。

原因と対策を見る

原因

  • ページ読み込み時に全画像をダウンロード
  • ビューポート外の画像も帯域を消費
  • 初期表示が遅くなりLCPに悪影響
  • モバイルではデータ通信量の無駄

対策

<!-- ネイティブ Lazy Loading -->
<img src="image.jpg" loading="lazy"
     width="800" height="600">

<!-- 重要な画像は eager（デフォルト） -->
<img src="hero.jpg" loading="eager">

<!-- Intersection Observer による実装 -->
const observer = new IntersectionObserver((entries) => {
  entries.forEach(entry => {
    if (entry.isIntersecting) {
      const img = entry.target;
      img.src = img.dataset.src;
      observer.unobserve(img);
    }
  });
});

document.querySelectorAll('img[data-src]')
  .forEach(img => observer.observe(img));

22. Web Font 読み込み

フォント読み込みによるFOUT/FOITとレイアウトシフト。

ABCDEFGabcdefg 12345 あいうえお

原因と対策を見る

FOUT と FOIT

  • FOIT (Flash of Invisible Text): フォント読み込み中、テキストが非表示
  • FOUT (Flash of Unstyled Text): 代替フォントで表示後、切り替わる
  • フォント読み込み後にテキスト幅が変わりCLSが発生
font-display 動作
auto ブラウザ依存（多くはFOIT）
block FOIT（3秒間非表示）
swap FOUT（即座に代替表示）
fallback 100ms非表示、3秒でスワップ
optional 100ms非表示、キャッシュ時のみ使用

対策

/* プリロードとfont-display */
<link rel="preload" href="font.woff2"
      as="font" type="font/woff2" crossorigin>

@font-face {
  font-family: 'MyFont';
  src: url('font.woff2') format('woff2');
  font-display: swap; /* または optional */
}

/* サイズ調整でCLSを軽減 */
@font-face {
  font-family: 'MyFont';
  src: url('font.woff2');
  size-adjust: 105%;
  ascent-override: 90%;
}

Canvas と描画

23. Canvas 描画

Canvasへの毎フレーム再描画。描画方法による負荷の違いを確認できます。

FPS: --
原因と対策を見る

原因

  • 毎フレームで全体をクリア→再描画
  • 複雑な図形の描画は CPU を消費
  • 高解像度ディスプレイでピクセル数が増加
  • 同期的な描画処理でメインスレッドをブロック

対策

  • ダーティレクト: 変更された領域のみ再描画
  • オフスクリーンCanvas: 静的部分を事前に描画してキャッシュ
  • レイヤー分離: 動的/静的要素を別Canvasに
  • WebGL: GPU アクセラレーションを活用
  • OffscreenCanvas: Web Worker で描画
// オフスクリーンCanvas でキャッシュ
const offscreen = document.createElement('canvas');
const offCtx = offscreen.getContext('2d');
// 静的な背景を一度だけ描画
drawBackground(offCtx);

function render() {
  // キャッシュを転送（高速）
  ctx.drawImage(offscreen, 0, 0);
  // 動的な部分のみ描画
  drawMovingObjects(ctx);
  requestAnimationFrame(render);
}

24. 大量パーティクル

パーティクルシステムによるアニメーション負荷。FPSの低下を確認できます。

パーティクル: 0 | FPS: --
原因と対策を見る

原因

  • 各パーティクルの位置・速度・色を毎フレーム計算
  • 描画コールの回数が増加
  • オブジェクト生成/破棄によるGC発生
  • 物理演算（衝突判定など）の計算コスト

対策

  • オブジェクトプール: パーティクルを再利用
  • 空間分割: 衝突判定の計算量を削減
  • LOD: 遠い/小さいパーティクルを省略
  • GPU パーティクル: WebGL/シェーダーで並列処理
  • バッチ描画: 同じ種類をまとめて描画
オブジェクトプール: 
class ParticlePool {
  constructor(size) {
    this.pool = Array(size).fill(null)
      .map(() => new Particle());
    this.active = [];
  }

  spawn() {
    const p = this.pool.pop() || new Particle();
    p.reset();
    this.active.push(p);
    return p;
  }

  recycle(particle) {
    const idx = this.active.indexOf(particle);
    if (idx > -1) {
      this.active.splice(idx, 1);
      this.pool.push(particle);
    }
  }
}

総合ストレステスト

12. すべてを同時実行

複数の問題を同時に発生させ、Performance タブで分析してみましょう。

分析のポイント

ストレステストで発生する問題

  • Long Task: 毎フレームの重い計算
  • Layout Thrashing: 200要素への読み書き
  • Forced Reflow: サイズ変更と読み取りの繰り返し
  • Memory 増加: オブジェクトの蓄積
  • Paint: アニメーションによる再描画

Performance タブでの分析方法

  1. レコーディングを開始
  2. ストレステストを実行（3-5秒）
  3. レコーディングを停止
  4. 以下を確認:
    • FPS: 緑のグラフ（理想は60fps）
    • CPU: 黄色のグラフ（100%に近いと問題）
    • Main: タスクの詳細（赤い三角を探す）
    • Summary: 処理の内訳

Chrome Performance タブの使い方

基本操作

  1. F12 または Cmd+Option+I で DevTools を開く
  2. "Performance" タブを選択
  3. 記録ボタンでレコーディング開始
  4. 問題のある操作を実行
  5. 停止ボタンで停止

見るべきポイント

表示 意味 対策
赤い三角 Long Task (50ms超) 処理を分割、Web Worker使用
紫 (Layout) レイアウト計算 DOM読み書きを分離
緑 (Paint) 描画処理 transform/opacity を使用
黄 (Script) JavaScript 実行 処理の最適化

便利な機能

  • CPU throttling: 低スペック環境をシミュレート
  • Network throttling: 遅い回線をシミュレート
  • Screenshots: 各時点の画面をキャプチャ
  • Call Tree: 関数の呼び出し階層を確認
  • Bottom-Up: 最も時間のかかった処理を確認

追加ツール

  • Rendering タブ: Paint flashing で再描画を可視化
  • Layers タブ: レイヤー構成を確認
  • Memory タブ: メモリ使用量とリークを確認
  • Coverage タブ: 未使用コードを検出
